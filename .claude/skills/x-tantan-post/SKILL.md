# 淡々施策系 X投稿ジェネレーター

改行なしで、具体的な施策を数字つきで淡々と言い切るX投稿を作る。
目指すのは「読んだ人がそのまま明日やれる」投稿。フォロワーが保存したくなるのは、気づきや精神論ではなく、すぐ使える手順と判断の基準だから。

## このスタイルの元になった投稿（ユーザー本人のもの）

> 個人開発で実際にアプリを作り始めるのは需要検証終わってからが絶対にいい。少額（5000円程）でSNS広告回してCPA100-300円取れてようやく開発に着手出来る。見切り発車でトークンの無駄遣いは勿体無い。

この投稿の強さは次の4つ。新しく作る投稿もすべてこの4つを満たすこと。

1. **1文目で言い切る**：「〜が絶対にいい」「〜すべき」「〜はやめた方がいい」。迷いを見せない
2. **具体的な数字が入っている**：5000円、CPA100-300円のように、読んだ人がそのまま真似できる数字
3. **判断の基準がある**：「この数字が取れたら次へ進む」という合格ラインがある
4. **最後に損得で締める**：「〜は勿体無い」「〜で利益はほぼ決まる」のように、やらないと損する理由で終わる

## 書き方のルール

- **改行しない**。1投稿＝1段落。改行すると「淡々と述べている」感じが消えて、よくある箇条書き投稿と同じに見えてしまう
- **だ・である調（常体）**。「です・ます」「！」「（笑）」「絵文字」は使わない。感情を乗せずに事実と施策を並べるのがこのスタイルの信頼感のもと
- **ハッシュタグ・URLは入れない**（ユーザーから指示があれば別）
- **1投稿1施策**。複数のことを詰め込まず、1つの施策を「結論→やり方（数字）→判断基準→損得」で深く書く
- **文字数**：X無料版は加重280まで（日本語・全角記号は1文字=2、半角英数字は1）。目安は日本語で100〜135字。上限ギリギリだと、ユーザーが少し手直ししただけで超えるので、260以下に収める
- **数字の扱い**：投稿に入れる数字は「目安」「経験則」として書く。架空の調査結果や統計（「〇〇調査によると73%が…」など）は作らない。出典のある数字を使うときは、本当に確認できるものだけにする。ツール会社のブログや又聞きのデータは「〜という目安がある」のように目安として書き、「〇〇の調査では」と権威づけはしない

## 型（どれか1つを選んで書く）

テーマが同じでも型を散らすと、タイムラインで単調に見えない。10本なら4種類以上、5本なら3種類以上を目安に混ぜる。

| 型 | 1文目の形 | 例 |
|---|---|---|
| 順番を正す | 「AはBが終わってからが絶対にいい」 | 開発は需要検証が終わってから |
| 常識を否定する | 「Aはやめた方がいい」 | 競合がいない市場を探すのはやめた方がいい |
| 比べて勝ちを示す | 「AよりBの方が効く」 | 機能を削るより対象を削る方が効く |
| 見るべき数字を示す | 「最初に見るべき数字はAではなくB」 | DAUではなく7日後の継続率 |
| 最低条件を示す | 「Aに必要なのはBの5つだけ」 | LPに必要なのは見出し・悩み・解決策・価格・ボタン |
| 証拠の基準を示す | 「Aは〇〇の証拠にならない」 | 「いいアイデアだね」は需要の証拠にならない |

## 手順

調査（手順2）と被りチェック（手順3・6）は、本数が少なくても、急いでいると言われても省かない。同じアカウントで似た投稿が続くと、フォロワーは「またこの話か」と感じてミュートや離脱につながる。毎回新しい切り口を出すことが、このアカウントの価値そのもの。

1. **テーマと本数を確認する**。指定がなければ、テーマは「個人開発×プロダクトマーケ（需要検証・集客・価格・継続率・MVP・LP）」、本数は10本。ユーザーが自分の体験や数字を書いていれば、それを最優先で使う

2. **過去投稿を把握する**。次のすべてに目を通し、「もう使った施策」を頭の中でリストにする
   - `references/posted-log.md`（これまでに作った投稿の全記録）
   - この会話の中で、すでに出した投稿
   - ユーザーが貼った最近の投稿や、過去投稿のファイル（あれば）
   被りとは、文章が似ていることだけではない。言い回しが違っても、同じ施策（例：「少額広告でCPAを見てから開発」）を同じ結論で言っていれば被りとみなす

3. **Webで調査する**。WebSearchなどの検索ツールで、テーマについて最低3回検索する。目的は、過去投稿にない新しい施策や切り口を見つけること。検索の例：
   - テーマの最新の事例や、海外の個人開発者（indie hacker）の公開事例
   - 新しいツールやプラットフォームの変化（広告の仕様、AIツール、アプリストアの規約など）
   - 相場の数字（CPA、CVR、継続率、価格帯など）。投稿に入れる数字の目安を、思い込みではなく調べた値に寄せる
   調査をもとに、過去投稿と被らないネタを本数の1.5倍くらい出してから、良いものを選ぶ。`references/topic-bank.md` のネタ帳も参考にしてよいが、＊印は使用済み。
   投稿の数字の根拠にする記事は、検索結果の要約だけで済ませず、できるだけページを開いて数字を確かめる。
   検索ツールがない環境では、調査できなかったことをユーザーに伝えたうえで、ネタ帳と知識で作る

4. **型を割り振って書く**。上の表から型を選び、「結論→やり方（数字）→判断基準→損得」の順で書く

5. **文字数を検証する**。1行1投稿でテキストファイル（posts.txt）に書き出す。置き場所は作業用の一時フォルダにして、スキルのフォルダには置かない。スクリプトで数える：
   ```bash
   python3 <このスキルのディレクトリ>/scripts/count_x.py posts.txt
   ```
   「OVER」や「目安超え」が出たら、削っても意味が変わらない言葉（「実際に」「本当に」「〜ということ」など）から削る

6. **被りをスクリプトでチェックする**。過去投稿ログ（とユーザーが渡した過去投稿ファイル）と照合する：
   ```bash
   python3 <このスキルのディレクトリ>/scripts/check_overlap.py posts.txt <このスキルのディレクトリ>/references/posted-log.md
   ```
   「被りの疑い」が出た投稿は、別のネタに差し替える。スクリプトは文字の似かたしか見ないので、OKが出ても、手順2で書き出した「使用済みの施策」と趣旨が同じものがないかを目でも確認する

7. **読み直す**。次に当てはまる投稿は書き直す
   - 改行や「！」、です・ます調が混ざっている
   - 数字がなく、精神論になっている（「大事なのは継続」など）
   - 他の投稿と言っていることがほぼ同じ
   - 締めの言葉（「勿体無い」など）が他の投稿と被っている。「〜で決まる」「〜だけになる」「〜の方がはるかに早い」などに散らす
   - 出典のない統計を事実のように書いている

## 出力の形

各投稿をコードブロックに入れて番号を振る（ユーザーがそのままコピペできるように）。最後に、文字数の検証結果を1行で書き添える。

```
**1**
（投稿本文）

**2**
（投稿本文）
```

文字数：全10本、加重〇〇〜〇〇/280で上限内
被りチェック：過去投稿〇〇本と照合し、被りなし

その下に、次の2つを短く添える。
- **調査で参考にしたもの**：投稿のネタになった記事や事例のリンク（3〜5個）
- **記録用**：今回の投稿をログに足すためのブロック。スキルのファイルに書き込める環境（Claude Codeでリポジトリにスキルがある場合など）なら、ユーザーが投稿を採用した時点で `references/posted-log.md` の末尾に直接追記する。書き込めない環境では「投稿したものは次回の依頼時に貼ってもらえれば、被りチェックの対象に入れます」と一言伝える

数字が経験則であることや、ユーザーの実体験の数字に差し替えると説得力が増すことは、必要なときだけ一言添える。毎回長い注意書きは書かない。

## 参考資料

- `references/posted-log.md`：これまでに作った投稿の全記録。被りチェックの照合先。毎回、書き始める前に読む
